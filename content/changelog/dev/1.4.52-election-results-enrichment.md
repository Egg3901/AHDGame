Cut from development.

## Added

- `GET /api/public/v1/elections?results=true` now returns `seatsEstimate` on
  multi-seat races: a projected seat count per candidacy. Single-seat races
  such as the Senate or a governorship leave the key absent, so a client that
  tests for it is unaffected.

- Each entry in the opt-in `results.candidates[]` now carries `favorability`
  and `politicalInfluence`, read from the candidate's character or, for a
  non-party candidacy, from their NPP. Either reads null when no such record
  exists.

- Those results entries also carry `id`, the candidacy id. It is the key
  `seatsEstimate` uses, so a seat split can be lined up against the standings
  without a second request.

## Fixed

- `GET /api/public/v1/elections/[id]` listed `favorability` and
  `politicalInfluence` on every candidate but always returned null for both.
  They now carry the same figures as the list endpoint.

- The two endpoints disagreed about which races count as multi-seat, so the
  same race could report a seat split on one and not the other. Both now apply
  the same rule.

## Changed

- `results.candidates[].characterId` has never held a character id. It holds
  the candidacy id, and does not join against the `characterId` on the main
  candidate list. The value is unchanged and the field stays, but it is now
  documented as an alias of `id` and the API guide points callers at `id`.

- The default election list response is unchanged and still costs the same
  queries. The candidate lookups behind the new figures run only when
  `results=true` is passed.
